## A1．修正完整规则预览

**问题与收益**：实施前，`selectorMatcher.ts` 逐项匹配 `matches` 并合并节点，把上下文也当成点击目标；上下文缺失时仍可能显示命中，影响风险评分、排序与高亮。本轮已修正规则层语义，并让各调用方共用结果。

**范围**：`src/lib/selectorMatcher.ts`、`selectorAdapter.ts`、`selectorSerialize.ts`，以及调用方 `selectorStrategies.ts`、AI 候选预览。复用官方单个 selector 解析／匹配能力，补齐规则层条件判断；不要另写选择器语法解析器。实施时重新查询图谱调用方与相关测试。

**验收**：

- [ ] `matches: [标题, 按钮]`：两项都满足时，只把最后一项的目标标为点击目标；标题作为上下文呈现。
- [ ] 任一必需项无匹配或语法无效时，不显示该规则可执行，也不沿用部分匹配制造成功结果。
- [ ] 内置候选与 AI 候选使用一致语义；计数、评分和画布引用同一份结果。
- [ ] 对界面已经接受的 `anyMatches`、排除条件和组级继承，按实际 GKD 语义处理；尚不支持的字段标为“未完整验证”，原文完整保留。
- [ ] 回归覆盖单项、多项、上下文缺失、多个目标、显式 `@`、非法表达式，以及已支持的组合条件；代表性样例与目标 GKD 的实际行为一致。

**证据**：前序偏差已转为回归并修复：标题与按钮都在时只把末项按钮作为点击目标；标题移除后该规则不满足。单条规则内 AND、多条独立规则 OR、分支／排除、显式目标和版本未知项均有公开入口回归；真机对照待验收。[官方规则字段语义](https://gkd.li/api/interfaces/rawruleprops#matches)

## A2．区分快照匹配与实际运行条件

**收益**：避免把“当前快照命中一个节点”解释成“真机一定有效”。

**范围**：预览结果、候选详情、测试状态；涉及 `activityIds`、`matchRoot`、时机及次数限制的解释。沿用现有场景设置。

**验收**：

- [ ] 计数明确属于当前快照；“已发送测试”“静态匹配”“用户确认有效”分别记录和呈现。
- [ ] 依据快照可确定的应用、Activity、条件不满足，给出具体原因；冷却、次数、前置步骤等缺少运行状态时标为未知，不推定通过。
- [ ] 全树预览不能证明事件节点查询范围也能匹配；只有取得相应数据时才展示运行范围结论。
- [ ] 显示必要的快照时间信息；重新采集或切换应用后，不误用旧结果。采集期间界面是否变化，若无接口证据则明确无法判断。

**依据**：[#669 排除条件的查询范围](https://github.com/gkd-kit/gkd/issues/669)、[#1037 采集耗时与界面变化](https://github.com/gkd-kit/gkd/issues/1037)。

## B1．重叠控件与点击范围确认

**收益**：用户能分清文字、关闭图标、外层按钮和广告热区，减少在同区域候选中盲试。

**范围**：复用 `src/lib/nodePicker.ts`、`regionCandidates.ts` 与 `src/components/ScreenshotCanvas.tsx`，在 Android 工作区提供简短目标列表。

**验收**：

- [ ] 多个有意义节点重叠时可切换目标；列表包含标签、可点击性及对应范围，不只显示节点编号。
- [ ] 区分用户选中的节点与最终执行点击的节点；自动选择可点击父节点时能看见变化并重新选择。
- [ ] 无可用节点时给出重新采集等恢复入口；不把整屏容器包装成可靠关闭按钮。
- [ ] 单一明确目标不增加必经确认；缩放、拖动后范围仍与截图对齐，并支持列表选择。

## B2．候选条件可编辑

**收益**：自动生成不理想时，用户可以直接调整条件，无需每次重新复制 prompt。

**范围**：从当前候选进入编辑，先支持文字／描述等于或包含、资源 ID、类型、可点击与可见条件；上下文先支持一个父子或相邻关系。复杂规则继续使用现有高级编辑路径。

**验收**：

- [ ] 可以增删改支持的条件，修改后即时重新校验、计数并高亮；取消编辑可恢复原候选。
- [ ] 条件值统一转义，带引号、反斜杠或中文时不产生错误表达式。
- [ ] 动态倒计时不默认锁死某一秒；多个匹配时支持补上下文，并说明会选择其中一个目标，不表述为“全部点击”。
- [ ] 只有整条规则可完整表示时才反解为条件；遇到不支持的表达式或字段，保留原文并进入高级编辑，绝不丢条件。
- [ ] 修改规则后，旧的“有效”测试结果不沿用为新规则的通过证据。

## B3．范围、时机与动作摘要

**收益**：用户不用阅读 JSON5 就能判断这条规则做什么、何时生效。

**范围**：候选卡片、详情及 `src/data/ruleSettings.ts` 的场景参数。复用现有预设，不统一改写所有场景的默认值。

**验收**：

- [ ] 摘要能表达目标、点击方式、页面范围与关键限制，例如“点击关闭按钮；仅当前页面；进入页面后 10 秒内；最多一次”。
- [ ] 摘要从最终有效字段生成，考虑组级继承；与测试、复制、导入内容一致。
- [ ] 周期弹窗不套用开屏短窗口；有匹配时间限制时说明它从相应重置时点计算，不解释为每次弹出重新计时。
- [ ] selector、分数和 JSON5 放在详情；常规操作不增加长篇教程或必经确认。

## B4．失败原因与修复反馈

**收益**：将“无效，再换一条”变成有方向的修复。

**范围**：复用 `src/lib/inlineRuleTesting.ts`、`helpPrompt.ts`、`aiModel.ts` 及当前测试管理界面。

**验收**：

- [ ] 至少区分目标节点不可用、静态条件不满足、范围／时机待核对、已匹配但动作无效、误触；“已匹配”需有证据或明确为用户反馈。
- [ ] 只呈现能证实的原因；没有运行日志时显示待排查项，不把猜测写成诊断事实。
- [ ] 每类失败提供一项相关操作，例如重新采集、调整范围、选择父节点或补充测试反馈。
- [ ] AI 反馈携带规则内容、快照身份、具体症状和已知限制；AI 修订后重新校验，不自动标记有效。

## C1．已有本地规则识别

**收益**：避免反复创建已经有规则处理的目标，并支持先查看现有规则再决定是否新增。

**前置调查**：当前客户端只有本地规则追加能力。先核对 fork 是否提供可用的只读接口；没有则单列接口需求，不假装已完成检测。

**验收**：

- [ ] 首版只读当前应用适用的本地规则，核对启用状态、页面及版本条件；后台检查不阻塞选点和预览。
- [ ] “选择器重复”与“不同规则覆盖同一目标”分别提示；静态覆盖不等于证明规则实际已触发。
- [ ] 默认提供查看与继续创建；替换必须具备稳定规则身份和明确写入接口。接口不可用时不出现虚假的编辑／替换入口。
- [ ] 不按组名或 selector 相同擅自覆盖外部规则；订阅规则库既定的完整规则组复制、导入与未测试可用策略保持一致。
- [ ] 读取失败时提示未检查，仍保留现有复制／导入路径。

## C2．多快照正反例验证

**收益**：防止只适合一张截图的规则被误认为稳定；特别检查假关闭按钮、倒计时变化和其他页面同名按钮。

**范围**：一条规则在多张独立快照上验证，与现有按多张快照编排步骤的功能分别呈现。

**验收**：

- [ ] 支持指定“应该匹配”和“不应该匹配”的快照，逐张显示结果及点击目标。
- [ ] 覆盖动态文案、重复 ID／按钮、广告消失后的页面、跨页面同名目标，以及父层广告热区。
- [ ] 误命中反例会明确提示，不能用总体平均分隐藏；所有通过仍只称静态验证通过。
- [ ] 使用脱敏或人工构造样例建立回归集，标明来源与预期，不把用户完整快照自动上传。

## D1．捕获后直接进入工作区

**收益**：缩短从“正在看到弹窗”到开始制作规则的路径。

**验证范围**：先调查 GKD 现有捕获入口、可调用接口与 Android 跳转能力，再选择最小实现；仅凭 WebView 不足以承诺跨应用悬浮捕获。

**进入实施的条件**：

- [ ] 设备原型验证按钮隐藏、截图／节点捕获、打开工作区、保存后返回的完整顺序。
- [ ] 验证权限丢失、采集失败、弹窗窗口、页面切换和无节点状态；保留原有快照入口作为恢复方式。
- [ ] 明确临时采集与用户已保存快照的区别、清理时机，以及进程退出后的行为。

## D2．录制一次点击来选目标

**收益与边界**：用于辅助选目标，成功后进入现有规则制作流程；不扩展为宏脚本或多动作录制。

**进入实施的条件**：

- [ ] 原生 View、WebView、长按、Compose、自行消失目标在支持版本上分别记录结果；上游模拟器证据不替代本项目验收。
- [ ] 能在整个录制期间暂停 GKD 规则执行，避免录入 GKD 自己的动作，并可靠恢复暂停前状态；只有 Rule Studio 自身停止发送测试不够。
- [ ] 事件能可靠映射到点击前快照的节点；没有事件、节点歧义或点击前画面变化时如实失败，保留截图选择。
- [ ] 当前 fork 不具备事件与暂停接口时停留在可行性结论，不以坐标猜测冒充成功。

## 本轮不直接照搬的建议

- 不因对方首版采用文字优先，就改掉本仓库的资源 ID 与多策略排序；先用 C2 样例和设备证据比较。
- 不统一清空 Activity、禁用所有 `fastQuery`，也不将所有场景改成同一匹配时间；按正确性证据逐项调整。
- 保留现有离线生成、场景预设、真机测试、多步骤与高级 JSON 能力；条件编辑以支持的子集切入。
- AI 继续作为候选生成与解释工具，其输出要走相同校验和测试流程。
- 现阶段不增加云端规则服务、自动更新已导入规则、远程订阅覆盖检测或新的选择器语言。
