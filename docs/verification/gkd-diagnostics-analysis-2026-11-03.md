## 这份样本实际能证明什么

### 一次有返回结果的 B 站点击

去重后的保留证据中，有一次动作返回：

| 北京时间 | 证据 | 可作出的判断 |
| --- | --- | --- |
| 16:54:08.528 | `runId=9210`，`query_started` | 开始一次查询任务 |
| 16:54:08.565 | `action_started`，规则 `666/2/tv.danmaku.bili/-1/index:0` | 订阅 666 的 B 站规则开始执行动作 |
| 16:54:08.565 | 两条 `action_target` 记录，目标均为 `tv.danmaku.bili:id/count_down` | 可定位本次操作节点；两条目标观察不等于点击两次 |
| 16:54:08.585 | `action_succeeded`，`clickNode`，`result=true` | 节点点击调用返回成功；动作开始到返回约 20 ms |
| 16:54:08.638—08.646 | 同一任务 `foreground_conflict`，进入 Cancelling、Cancelled | 随后发生前台冲突并取消任务；不据此判定点击失败或取消原因是 GKD 缺陷 |

节点边界为 `[899, 2530, 1208, 2684]`，可见性为 true，记录也包含目标文字。未在报告中复制界面文字。

整个样本有四条 Action 阶段事件，分别为开始、两条目标观察、一次结果。**不能统计成四次点击。** 本报告只确认“保留证据中有一次成功返回的点击”，不把它当作全程完整计数或广告确已关闭的证明。

### 实际运行规则可以从诊断材料里找到

现场同时选入两个订阅的 B 站“开屏广告”规则：

| 订阅 ID | 订阅版本 | 组 key / 规则位置 | 该样本中的定义 |
| --- | --- | --- | --- |
| 666 | 406 | -1 / index:0 | `[vid="count_down" || vid="skip"][visibleToUser=true]` |
| 667 | 623 | -1 / index:0 | 同上 |

两者均记录 `actionCd=500 ms`、`actionMaximum=2`、`fastQuery=true`、`resetMatch=app`。动作返回证据归属于订阅 666。

这说明反馈需要保留实际运行规则的**订阅 ID、订阅版本、应用、规则组 key、规则 key 或 index，以及实际生效参数**。只附相同选择器或工作区草稿，不能准确区分运行来源。

可能的解释：如果另一条规则已经消除了目标，后续查询可能不再匹配。该样本不足以证明订阅 667 的未匹配就是由此造成；本次未禁用任一订阅进行对照试验，不能归因。

### 可以观察筛选、取消与查询耗时

- 现场规则快照有 14 份，观察到 GKD、桌面、B 站、本工具共四个应用上下文。
- GKD 和桌面现场记录 `blockMatch=true`；B 站现场 `blockMatch=false`。不能把前者的未执行直接当规则失效。
- 原始原因中包含冷却 `Cooldown`、前台冲突、来源与前台不一致、无可用规则等。应按原因解释，不把每条取消或过滤都显示成错误。
- 保留的 32 份详细查询证据中，30 份 `not_matched`、2 份 `cancelled`；查询耗时约 `3.34—70.65 ms`。这里只是该样本测量，未建立性能基线，不宣称存在性能回归。
- `completed=true` 不能翻译成“匹配成功”：本样本的全部 32 份查询证据均 completed，但 outcome 仍有未匹配与取消。

## 完整性与缺少的材料

| 项目 | 样本结果 | 对反馈判断的影响 |
| --- | --- | --- |
| 三个事件流 | events 2000、keyEvents 2000、boundaryEvents 13 | 共有 964 条重复副本；按 sequence 合并后是 3049 条，不是 4013 次独立事件 |
| 重复一致性 | 同 sequence 的副本全部一致 | 本样本可按 sequence 去重；不同会话仍须带会话 ID |
| 主事件淘汰 | session.dropped = 2281 | 保留的主事件流不覆盖完整过程 |
| 关键事件淘汰 | droppedKeyEvents = 326 | 关键流同样不保证完整 |
| 详细查询淘汰 | droppedQueryRecordings = 4 | 仅凭现存查询全为未匹配／取消，不能否定动作流中已有的成功点击 |
| 查询记录上限 | 官方该版本在 recordSystem=true 时保留最近 32 份 | 与本样本淘汰现象一致；不将有淘汰误报为 JSON 损坏 |

| 用户预期与复现说明 | 诊断无法替用户表达 | 仍需用户写明希望发生什么、实际看到什么、如何重现 |

## 据此建议的反馈收集范围（待讨论，未实现）

| 反馈展示项 | 数据来源 | 用途 |
| --- | --- | --- |
| 问题描述、复现步骤、预期与实际表现 | 用户填写 | 让开发者知道要验证什么 |
| GKD 版本、采集区间、目标应用与页面 | 会话、规则快照、运行状态 | 对齐环境与发生时间；不要误用顶层生产者 appId |
| 实际运行规则与其它相关候选规则 | ruleDefinitions、ruleSnapshots | 区分工作区草稿与 GKD 实际运行版本，也能发现相同选择器的多个来源 |
| 执行摘要与最后可见原因 | 合并去重的事件、查询结果、动作返回 | 显示“是否进入候选／查询／动作、返回什么、为何取消或过滤” |
| 材料完整性 | dropped、droppedKeyEvents、droppedQueryRecordings、trackingComplete | 明确“完整收尾但部分记录淘汰”，避免虚假的零触发结论 |
| 截图或必要节点现场 | 用户自选并预览 | 补充日志不能表达的视觉结果 |

对“当前规则”可以采用更明确的来源标识：`GKD 实际运行规则` 与 `工作区草稿`。导入诊断后，可以让用户选择其中的实际运行规则，避免要求用户凭记忆寻找同一版本；此处只是产品建议。

不默认上传整个 ZIP。样本还包含数据库、设置、其它订阅、应用元数据和普通日志；诊断自身也有节点文字、选择器、应用与页面信息。应由用户选择会话和目标规则，展示拟提交摘要，允许检查或隐藏敏感内容。筛选时保留会话、sequence、runId 与规则引用的对应关系；目前尚未实现或验证自动筛选、脱敏及附件导入。
